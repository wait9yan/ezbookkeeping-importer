# v0.3.1 发布说明

修复月账单“确认新建”后仍被发送前查重拦截的问题，并收紧普通重复候选范围，避免相邻日期的独立消费互相阻塞。

## 修复与行为变化

- 月账单普通候选必须同时满足：上海时区的同一交易日、同卡人民币账户、同符号结算金额、规范化后相同商户。相邻日期、仅入账日相同、不同商户或其他币种的同数值金额不再产生普通重复候选。
- 同卡隐藏人民币账户的历史账仍参与查重。已知来源标记独立核实，不因金额或账户被修改就当作不存在；原有写入结果不明的核实流程保持不变。
- `confirm-new` 保存已观察候选的关键字段快照。分类和发送前共用确认规则，只排除明确确认且未变化的候选；新增或变化的候选仍会阻止发送。
- 旧 `allow_new` 布尔值不再授予永久豁免。旧重复诊断若缺少候选快照，应先执行定点 `recheck`，仍有候选时再确认新建。
- 人工指定 `--target-id` 的关联能力保留：验证原日期范围、支出类型、同符号人民币金额及唯一对应账户，允许手工备注不同于银行商户文本。它与自动候选发现分别校验，不扩大账户和金额边界。

例如：8 月 22 日与 8 月 23 日同商户各 ¥4.68，普通查重现在将其视为不同日期的消费；同日同商户同金额仍需核实，不能仅凭金额相同就自动合并。

## 升级

本版本没有新增数据库迁移，结构版本仍为 **4**，业务配置无需新增参数。

从已完成迁移的 v0.3.0 升级，先停止 worker 和并发维护写入，配对备份数据库、邮件原件与配置。在 `.env` 固定 `EBKI_IMAGE=ghcr.io/wait9yan/ezbookkeeping-importer:0.3.1` 后执行：

```sh
docker compose stop importer
docker compose pull importer
docker compose run --rm importer doctor
docker compose up -d --no-build
docker compose exec -T importer ebki status
docker compose exec -T importer ebki issues --format text
```

已排队、仅因发送前检查阻塞的任务会在 worker 恢复后按新规则复核；停在 `duplicate_candidates` 的交易不会仅因换镜像自动重试，可用问题快照执行定点 `recheck`。仍有候选时按新快照处理；已有 `unknown` 任务继续核实，不盲目重发。

**从 v0.2.x 直接升级，仍须先遵循 [v0.3.0 升级说明](https://github.com/wait9yan/ezbookkeeping-importer/blob/v0.3.1/docs/releases/v0.3.0.md) 中的旧还款清理和配置调整。** 正常启动具备自动数据库迁移，但含旧还款数据的 003 迁移仍要求先运行一次性清理工具；本版本没有把该清理步骤自动接入启动。使用上述说明时应将镜像版本固定为目标 `0.3.1`。

收紧候选范围意味着已被用户改日期或商户文本、且没有可识别来源标记的手工账，可能不再被自动识别；需要时使用显式人工关联，不将“无候选”等同于完整历史无重复。

## 验证范围

修复已完成本地 621 项单元测试和最终 40 项相关 PostgreSQL 回归，Ruff、mypy、wheel/sdist 构建通过。覆盖相邻日、不同商户、跨币数值、隐藏账户、人工确认到发送、确认后新增/修改候选、窗口外变更、查询失败及显式人工关联。

本地完整数据库套件曾受 60 秒硬超时和共享测试锁竞争影响，未计作完整通过；正式发行的完整质量检查、PostgreSQL 17/18 × Bookworm/Alpine 与 AMD64/ARM64 镜像验收以标签工作流结果为准。本地验证不代表生产部署完成。
